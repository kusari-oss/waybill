# Feature Specification: Installed C/C++ library versions from pkg-config and CMake version files

**Feature Branch**: `1531-pkgconfig-cmake-versions`
**Created**: 2026-11-15
**Status**: Draft
**Input**: Issue #1531. Read pkg-config (`*.pc`) and CMake package version files (`*ConfigVersion.cmake`, `*-config-version.cmake`) as installed-tier evidence of exact library versions. An installed C/C++ SDK today yields almost no versions, though these files state them exactly.

## Background

An installed C/C++ SDK ships two kinds of metadata that state each library's version exactly:

- **pkg-config files** (`<prefix>/lib/pkgconfig/<module>.pc`). Each has a `Version:` field, plus `Requires:` (what a consumer also links) and `Requires.private:` (what a consumer also links only when linking statically).
- **CMake package version files** (`<prefix>/lib/cmake/<Package>/<Package>ConfigVersion.cmake` or `<package>-config-version.cmake`). These are usually generated by `write_basic_package_version_file`, and they set `PACKAGE_VERSION` to the installed version.

waybill reads neither. Its only mention of pkg-config is `apk.rs`, which skips Alpine's `pc:` dependency tokens. On an installed prefix, a library therefore appears only as a file-level binary component, `pkg:generic/<filename>?file-sha256=…`, with no version. A version appears only when one of the curated embedded-version scanners recognises the library (#1525, #1526).

The issue's measurement: one ROCm SDK payload held 44 `.pc` files and 78 CMake version files. The nine `.pc` versions sampled matched the versions of the source archives those libraries were built from. One `.pc` had a `Version` that was an unexpanded template (`${version}`).

### Identity, and why it is `pkg:generic`

purl-spec has no type for pkg-config modules or CMake packages. waybill already names an unmanaged C/C++ library `pkg:generic/<name>@<version>` in two places:

- the embedded-version scanners (`binary/entry.rs::version_match_to_entry`, the #1526 shape);
- the CMake reader's `find_package` declarations, whose names are lowercased (`cmake.rs`).

This feature uses the same shape, with a lowercased name. So a library this reader finds, and the same library at the same version found by an embedded-version scanner, have one canonical PURL. They merge through the existing identical-PURL deduplicator, with no new mapping. That is the same rule spec 1530's FR-009 set.

## Clarifications

### Session 2026-11-15

- Q: When a binary in the prefix matches a library (`libwaybill-fixture-a.so` ↔ `waybill-fixture-a.pc`), does the version go onto the binary's own file component, or is the library a separate component? → A: **A separate library component, with the matched binary listed in its evidence.** This is the shape the embedded-version scanners (#1525, #1526) already use. A library stated by a `.pc` and found by an embedded-version scanner at the same version therefore merges into one component. The binary's file component is unchanged, and no new edge kind is introduced (FR-010).
- Q: How is `Requires.private` recorded? → A: **As an ordinary dependency edge, like `Requires`, marked private by an annotation.** It lists what the library itself links (`libpng.pc: Requires.private: zlib`, and `libpng.so` loads zlib at run time). "Private" only describes what a *consumer* must link directly, and only when linking statically. So both are real dependencies of the library (FR-011).
- Q: What about a `.pc` or CMake version file that an installed OS package already owns, such as `/usr/lib/x86_64-linux-gnu/pkgconfig/zlib.pc` from dpkg's `zlib1g-dev`? → A: **It is skipped, and counted under `owned-by-os-package`.** The OS package component already identifies that library, and a second `pkg:generic` identity on every distro image would be a duplicate. Ownership means appearing in the file list of an OS package database: dpkg, rpm, apk, alpm, opkg or Homebrew. Files anywhere else are read, including inside Python wheels and unpacked SDK prefixes, where these files are the only per-library versions (FR-015).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Every library an installed prefix declares gets its exact version (Priority: P1)

An engineer scans an installed SDK, either a directory tree or an image layer holding `/opt/<sdk>/lib`. It ships pkg-config and CMake version files for its libraries. They expect one versioned component per library, taken from those files, where today they get unversioned file components.

**Why this priority**: This is the whole of #1531. These files are exact, first-party statements of what was installed, and they are already on disk next to the binaries.

**Independent Test**: A synthetic prefix with three `.pc` files and two CMake version files, scanned as a directory. Every library appears once with its stated version.

**Acceptance Scenarios**:

1. **Given** `<prefix>/lib/pkgconfig/waybill-fixture-a.pc` with `Version: 1.2.3`, **When** the prefix is scanned, **Then** one component `pkg:generic/waybill-fixture-a@1.2.3` is emitted. It carries `waybill:source-mechanism: pkg-config`, and its evidence names the `.pc` file.
2. **Given** a `.pc` that defines `version=2.0.1` and declares `Version: ${version}`, **When** it is scanned, **Then** the version is `2.0.1`, the way pkg-config itself resolves it.
3. **Given** a `.pc` whose `Version` still holds an unresolved template after expansion (`${version}` with no such variable, or `@VERSION@`), **When** it is scanned, **Then** no component is emitted for it. The skip is counted in the document and named in a warning.
4. **Given** `<prefix>/lib/cmake/WaybillFixtureB/WaybillFixtureBConfigVersion.cmake` with `set(PACKAGE_VERSION "4.5.6")`, **When** it is scanned, **Then** one component `pkg:generic/waybillfixtureb@4.5.6` is emitted, carrying `waybill:source-mechanism: cmake-package-version`.
5. **Given** a library with both a `.pc` and a CMake version file stating the same lowercased name and version, **When** it is scanned, **Then** one component is emitted. It carries `pkg-config` as its C55 value and both files as evidence. Recording the second mechanism in C56 `also-detected-via` is deferred to #1558, which has never been wired. *(Amended during planning: research R4.)*

---

### User Story 2 — The libraries' declared dependencies become edges (Priority: P1)

The same engineer wants the dependency relationships the SDK itself declares: `waybill-fixture-a` requires `waybill-fixture-c`.

**Why this priority**: Without edges, every library is a parentless component and the document's graph says nothing about the SDK's own structure. `Requires` is the SDK's first-party statement of it.

**Independent Test**: In the US1 prefix, `waybill-fixture-a.pc` lists `Requires: waybill-fixture-c >= 1.0` and `Requires.private: waybill-fixture-d`. `waybill-fixture-a` depends on both, and only the edge to `waybill-fixture-d` is marked private.

**Acceptance Scenarios**:

1. **Given** `Requires: waybill-fixture-c >= 1.0, waybill-fixture-e`, where both modules have `.pc` files in the same prefix, **When** it is scanned, **Then** `waybill-fixture-a` depends on both components. The version constraint is not treated as the target's version: the target's own `.pc` states that.
2. **Given** a `Requires` naming a module with no `.pc` anywhere in the scan, **When** it is scanned, **Then** no component is fabricated for it, and the unresolved requirement is counted in the document.
3. **Given** a `Requires.private` entry naming a module in the scan, **When** it is scanned, **Then** it is an ordinary dependency edge, and the component records that the edge is private.
4. **Given** a module listed in both `Requires` and `Requires.private`, **When** it is scanned, **Then** there is one edge, and it is not marked private.

---

### User Story 3 — The binaries in the prefix are tied to their library (Priority: P2)

The prefix also holds the shared libraries themselves (`lib/libwaybill-fixture-a.so.1.2.3`). Today the binary scan emits each as a file component with no version. The engineer wants the versioned library's evidence to name the files that ship it, the way an embedded-version match already names the binary it was read from.

**Why this priority**: It makes the versions reach the artifacts that ship. It ranks P2 because US1 already gives the correct component list, while this links evidence.

**Independent Test**: The US1 prefix with an ELF shared library whose file name and soname match `waybill-fixture-a`. The library component's evidence lists the binary's path, and the binary's own file component is unchanged.

**Acceptance Scenarios**:

1. **Given** a binary in the same prefix whose soname or file name matches a pkg-config module (`libwaybill-fixture-a.so.1` ↔ `waybill-fixture-a`), **When** it is scanned, **Then** the library component `pkg:generic/waybill-fixture-a@1.2.3` lists the binary's path in its evidence. The binary's file component is emitted exactly as today, with no version added and no new edge.
2. **Given** a binary that matches no module, **When** it is scanned, **Then** it is emitted exactly as today.
3. **Given** a binary whose name matches modules in two different prefixes, **When** it is scanned, **Then** it is related only to the module in its own prefix.

### Edge Cases

- **Source and build trees.**
  - A source tree carries `.pc.in` and `ConfigVersion.cmake.in` templates. These are not read, because their suffix differs.
  - A generated `.pc` or version file committed under a test directory is read only if it sits in a recognised install location (FR-001, FR-006). A stray `.pc` at a repository root is not.
  - Nothing under a directory the shared walker skips is read, whatever its location: dot-directories, `build/`, `out/`, `dist/`, `vendor/`, `target/`, `node_modules/` and the rest of the walker's default skip set. So `build/install/lib/pkgconfig/x.pc` is not read. The one exception is the Python virtual environments in FR-001. *(Amended during analysis: I1, research R1.)*
- **Several prefixes in one scan** (`/usr`, `/usr/local`, `/opt/<sdk>`). Each prefix's modules are resolved within that prefix first (FR-004). The same module at the same version in two prefixes is one component with both files as evidence. At different versions it is two components.
- **`Requires` syntax.** Entries are separated by commas or whitespace, and each may carry a comparison (`>=`, `<=`, `=`, `<`, `>`, `!=`) and a version. Comparisons are not versions of the target.
- **Variable expansion.** Variables are defined in the same file (`prefix=/opt/x`, `version=1.0`) and may reference each other. Expansion follows pkg-config: variables resolve recursively within the file. A cycle or an undefined variable leaves the value unresolved, and it is never guessed.
- **CMake version files that compute their version** (`set(PACKAGE_VERSION ${FOO_VERSION})`, or a version assembled in `if()` blocks). Only a literal `set(PACKAGE_VERSION "<literal>")` (quoted or bare) is read. Anything else is skipped and counted, never evaluated.
- **The same name with different versions** in a `.pc` and a CMake version file of one prefix. Both components are emitted, and nothing reconciles them, since FR-009 merges only identical PURLs. The disagreement is visible in the document and is counted.
- **Case.** CMake package names are case-sensitive file names (`ZLIBConfigVersion.cmake`), while `find_package` declarations are lowercased by the CMake reader. The name is lowercased so that the installed and declared identities meet (FR-003).
- **Symlinked prefixes** (`/opt/rocm` → `/opt/rocm-6.2.0`). A file reached twice through a symlink is read once, as the shared walker already guarantees.
- **Files an OS package owns.** On a distro image, nearly every `.pc` belongs to a `-dev` package that the dpkg, rpm or apk reader already emits. These files are skipped and counted (FR-015), so a distro image gains no `pkg:generic` duplicates. Where an OS package database is present but records no file list for a package, its files are not known to be owned, and are read.
- **Wheels that bundle an SDK.** A Python wheel shipping `lib/pkgconfig` or `lib/cmake` is read: the wheel's `pkg:pypi` identity names the bundle, not the libraries inside it. This includes a wheel installed into a project's `.venv/` or `venv/`, which is the common way an SDK wheel reaches a user. The shared walker skips those directories by default, so the reader opts into them (FR-001). *(Amended during analysis: C1.)*
- **Symlinks that leave the scan root.** In an extracted image, `usr/lib/pkgconfig/x.pc` may be an absolute symlink (`/opt/sdk/lib/pkgconfig/x.pc`). The target is resolved against the scan root, as the image itself would resolve it, never against the host. A target that escapes the root through `..` is not read, and is counted as `malformed` (FR-012). *(Amended during analysis: G1.)*
- **Malformed files** (binary content, a missing `Version:` field, an oversized file). These are skipped with a warning and counted. They never abort the scan.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The scan MUST read every pkg-config file (`*.pc`) found in a pkg-config search location under the scan root. That is a directory named `pkgconfig` whose parent is `lib`, `lib64`, `lib32`, `libx32`, `share`, or `lib/<multiarch-triplet>`, at any depth. This includes locations inside a Python virtual environment named `.venv` or `venv`, the same environments the pip reader reads (`pip/dist_info.rs::candidate_site_packages_roots`), although the shared walker skips those directories by default. It applies equally to FR-006's CMake locations.
- **FR-002**: For each such file whose version resolves (FR-005), the scan MUST emit one component. Its name is the module name, which is the file name without `.pc`, as `Requires` refers to it. Its version is the file's resolved `Version`. Its tier is installed (`deployed`). It carries `waybill:source-mechanism: pkg-config`, and its evidence names the file.
- **FR-003**: Component identity MUST be `pkg:generic/<lowercased-name>@<version>`, with both segments percent-encoded. This matches the embedded-version scanners and the CMake reader's `find_package` names.
- **FR-004**: Each `Requires` entry MUST become a dependency edge from the module's component to the component of the named module. The named module is resolved in the same prefix first, then anywhere in the scan, and only when exactly one candidate exists. Comparison operators and their versions MUST NOT become the target's version. An entry naming no module in the scan MUST NOT fabricate a component, and MUST be counted (FR-008).
- **FR-005**: The `Version` value MUST be expanded with the variables defined in the same file, recursively, the way pkg-config does. When the result still contains `${…}` or `@…@`, or is empty, the file MUST NOT produce a component, and the skip MUST be counted and warned.
- **FR-006**: The scan MUST read every CMake package version file (`<Package>ConfigVersion.cmake` or `<package>-config-version.cmake`) found in a CMake package search location under the scan root. That is any directory below a `cmake` or `CMake` directory whose parent is `lib`, `lib64`, `lib32`, `libx32`, `share` or `lib/<multiarch-triplet>`. It also includes `<prefix>/<Package>*/cmake/` and `<prefix>/<Package>*/CMake/`, the locations `find_package` searches.
- **FR-007**: For each such file, the package name MUST come from the file name, with the `ConfigVersion.cmake` or `-config-version.cmake` suffix removed. The version MUST come from a literal `set(PACKAGE_VERSION <literal>)`, quoted or bare. A file without such a literal MUST NOT produce a component; it is counted and warned. The component carries `waybill:source-mechanism: cmake-package-version` and the same identity rule as FR-003.
- **FR-008**: Whenever at least one file of either kind was seen, the document MUST carry one document-level coverage record, under a new catalog row with extractors in all three formats. It holds:
  - the files read, and the components emitted, per kind;
  - the skips per reason: `unresolved-version`, `no-version`, `computed-version` (CMake), `malformed`, `owned-by-os-package` and `unrecognised-location`, the last if a location rule rejected a file the walker matched by name;
  - the count of unresolved `Requires` entries;
  - the count of names whose `.pc` and CMake versions disagree within one prefix.

  A reason with a zero count is listed with zero. A document with no such files carries no record. Each skip is also a log warning naming the file.
- **FR-009**: A component from this reader MUST merge with another reader's component only when their canonical PURLs are identical: another `.pc`, a CMake version file, an embedded-version match, or a `find_package` declaration resolved to the same version. Different PURLs stay separate. No name-to-name mapping is introduced.
- **FR-010**: A library component's evidence MUST list the path of each binary in its prefix that matches it. The binary's own file component MUST NOT change: no version is added, and no edge is added. A binary MUST be matched only to a module in its own prefix, by file name, against the shared-library file components the binary scan emitted: `lib<module>.so`, `lib<module>.so.<N…>`, `lib<module>.dylib`, `lib<module>.<N…>.dylib`, or `<module>.so*` when the module name already begins with `lib`. *(Amended during planning: research R9. waybill reads no DT_SONAME or install name today, and it emits no file component for a static archive, which is #1534's territory.)* An ambiguous match, with more than one module, MUST list the binary under none.
- **FR-011**: Each `Requires.private` entry MUST become a dependency edge resolved exactly as FR-004 resolves `Requires`. The component MUST record, in an annotation with extractors in all three formats, which of its dependencies are private only. A module named in both lists is not private.
- **FR-012**: The reader MUST work offline, read only files under the scan root, run no subprocess, and evaluate no CMake or pkg-config code. Parsing is textual.
  - A symlinked file MUST be resolved against the scan root: an absolute target is taken relative to the root, as in an extracted image. A target that escapes the root MUST NOT be read.
  - The Homebrew keg check (FR-015) MUST resolve the same way.
  - No host path outside the scan root is ever opened or canonicalised on the reader's behalf.
- **FR-013**: Output MUST agree across CycloneDX 1.6, SPDX 2.3 and SPDX 3 for every value this feature adds, and be byte-identical across repeated scans of the same tree.
- **FR-014**: Directory scans and image scans MUST both read these files, subject to FR-015. An image scan of an image tarball is tested locally; the `image-postgres16` corpus golden in CI is a second check, not the only one. *(Amended during analysis: G2.)*
- **FR-015**: A file listed in the file list of an OS package database present in the scan (dpkg, rpm, apk, alpm, opkg or Homebrew) MUST NOT produce a component, and MUST be counted under `owned-by-os-package`. Its `Requires` entries MUST NOT produce edges. A file owned by a language package (for example inside a Python wheel, whose `RECORD` lists it) is not OS-owned, and is read.

### Key Entities

- **pkg-config module**: the `.pc` file name, its resolved `Version`, its `Requires` and `Requires.private` lists, and its prefix (the directory above its `lib`, `lib64`, `share` or `lib/<triplet>`).
- **CMake package version record**: the package name from the file name, the literal `PACKAGE_VERSION`, and its prefix.
- **Installed library component**: `pkg:generic/<name>@<version>`, tier `deployed`, with mechanism `pkg-config` or `cmake-package-version`. When the two merge, the `.pc` mechanism is kept and the evidence is the union of both files (research R4).
- **Installed-library coverage record**: the FR-008 document-level counts.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In the US1 fixture (three `.pc` files, one of them with an unresolved template, and two CMake version files, one with a computed version), the scan emits exactly three versioned components with the stated versions. The coverage record shows one `unresolved-version` and one `computed-version`. The released v0.16.0 emits zero versioned components for the same tree.
- **SC-002**: In the US2 fixture, the emitted edges equal the union of the `Requires` and `Requires.private` lists exactly. The private-only annotation names exactly the private-only targets. An unresolved entry produces no component and a count of one.
- **SC-003**: A library stated identically by its `.pc` and its CMake version file is one component. It has C55 `pkg-config`, tier `deployed`, and both files as evidence. A zlib `.pc` of version `V`, next to a zlib binary whose embedded version string the #1525 scanner reads as `V`, also gives one component: C55 `pkg-config`, tier `deployed`, with the binary's path in its evidence. Neither carries C56, which is deferred to #1558. *(Amended during planning: research R4.)*
- **SC-004**: Values added by this feature agree across all three formats in every fixture, and 10 repeated scans of each fixture are byte-identical.
- **SC-005**: A source-tree fixture holding `.pc.in` and `ConfigVersion.cmake.in` templates, a `.pc` at the repository root and a `.pc` under `tests/`, emits no component from them.
- **SC-006**: On a published ROCm SDK payload, scanned in CI and never locally, the `.pc` and CMake version files present are counted. Every one with a literal version yields a versioned component, or appears in the coverage record under a named reason, so the two totals add up exactly. The number of components with a version rises by at least the number of distinct library names those files state. The payload, its digest and both counts are recorded in the feature's measurements.
- **SC-007**: No committed golden changes, except those whose input tree contains a file this feature matches. Research R10 measured that 0 of the 20 git corpus targets contain one. `image-postgres16` names two (`nss_wrapper.pc` and `nss_wrapper-config-version.cmake`), which are expected to be dpkg-owned. So exactly its three goldens are predicted to change, each gaining a coverage record with `owned-by-os-package: 2` and no component. *(Amended during planning: research R10.)*
- **SC-009**: In a fixture with a dpkg database whose file list includes `usr/lib/x86_64-linux-gnu/pkgconfig/waybill-fixture-z.pc`, that file produces no component and the coverage record shows one `owned-by-os-package`. The same `.pc` with the database entry removed produces `pkg:generic/waybill-fixture-z@<version>`.
- **SC-008**: In the US3 fixture, the library component's evidence lists exactly the matching binaries of its own prefix. The binaries' file components are byte-identical to a scan with the `.pc` files removed, and an ambiguous binary is listed under no library.

## Assumptions

- `pkg:generic` is the identity type, because no purl-spec type exists for pkg-config modules or CMake packages. A future purl-spec type would be a separate change.
- The installed tier is `deployed`, as for every other installed-package reader (dpkg, rpm, apk, alpm, brew, opkg, dist-info).
- Fixtures use synthetic `waybill-fixture-*` names. No ROCm payload is downloaded or scanned locally; SC-006 is measured in CI.
- Zero new Cargo dependencies, and no subprocesses.
- Out of scope: a `.pc`'s `Description`, `URL`, `Cflags` and `Libs` fields; `Conflicts`; and CMake `*Config.cmake` files without a version file. Each could feed later work, but none states a version.
- Out of scope: inferring versions from library file names (`libfoo.so.1.2.3`). A soname version is an ABI version, not a release version, and the curated embedded-version scanners already own binary-derived versions.
- Notes for the cataloger interface (#1545): ROCm-specific layouts, such as a shipped manifest of source pins or prefix-renamed bundled libraries, belong to a project cataloger (#1541). This reader covers only the two formats every installed C/C++ SDK shares.
