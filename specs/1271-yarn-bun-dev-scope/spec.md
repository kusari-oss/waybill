# Feature Specification: yarn and bun development scope

**Feature Branch**: `1271-yarn-bun-dev-scope`
**Created**: 2026-11-01
**Status**: Draft
**Input**: Issue #1297, the yarn and bun portions, after #1314 closed pnpm v9. Format shapes measured in `measurements/findings.md`.

## Clarifications

### Session 2026-11-01

- Q: When a cross-reader classification disagreement turns up (FR-007), does it block? → A: Blocking only for disagreements this feature introduces; a pre-existing one is measured, recorded and filed as its own issue.
- Q: Must yarn workspace-member discovery honour `--exclude-path`? → A: Yes, along with the existing traversal safety guarantees; an excluded member contributes no development evidence and one diagnostic names the exclusion.
- Q: Does a development declaration using a non-registry protocol become a development seed? → A: No. Only a declaration resolving to a locked package in the lockfile's package map seeds classification, mirroring pnpm; a `patch:`-wrapped dependency going unclassified is an accepted, recorded limitation.

## User Scenarios & Testing

### User Story 1: Exclude development tooling from a bun project (P1)

An operator scanning a bun project can distinguish development-only dependencies and exclude them, including their transitive closure, while retaining everything reachable at runtime.

Why first: the axis is in the lockfile, so the evidence is self-contained and the classification rule is the one #1314 already proved for pnpm v9. It ships without touching any manifest-reading path.

Independent test: scan a `bun.lock` generated by bun 1.4.2, before and after `--exclude-scope dev`, in all three formats.

Acceptance scenarios:
1. A dev-only declaration and its transitive closure are removed; the runtime closure is retained.
2. A package declared under `devDependencies` by one workspace and reachable from another workspace's runtime dependencies remains runtime.
3. A dev declaration reachable transitively from a runtime declaration remains runtime.
4. An `optionalDependencies` declaration is not demoted to development.
5. Two locked versions of one package are classified independently.
6. A workspace member's dev declaration is honoured, keyed by its workspace path.

---

### User Story 2: Exclude development tooling from a yarn project (P2)

An operator scanning a yarn project gets the same distinction, for both the v1 and Berry lockfile dialects.

Why second: neither dialect records the axis, so the classification must be seeded from a `package.json` on disk. That makes it dependent on evidence outside the lockfile and able to degrade in ways US1 cannot, so it follows the simpler case rather than leading it.

Independent test: scan a v1 `yarn.lock` (yarn 1.22.22) and a Berry `yarn.lock` (yarn 4.18.1) over the same manifest, before and after `--exclude-scope dev`, and confirm both produce the same classification.

Acceptance scenarios:
1. A `devDependencies` entry in the root manifest and its transitive closure are removed; the runtime closure is retained.
2. The v1 and Berry readings of one manifest classify the same package set.
3. A package in both `dependencies` and `devDependencies` is runtime.
4. Milestone 181's optional classification and `peerDependenciesMeta` precedence are unchanged.
5. An npm-aliased dev declaration is classified by its resolved identity, not its local name.

---

### User Story 3: A document that cannot be filtered says so (P3)

An operator whose project cannot be classified learns it from the scan rather than from a document that looks filtered.

Why third: it is the complaint #1297 actually makes — `--exclude-scope dev` removing nothing is not an error and emits no warning — but it is only observable once US2 exists: bun needs no manifest on disk, so none of these diagnostics can arise there.

Independent test: scan a yarn project whose `package.json` is absent or unparseable and confirm the diagnostic names the reader, the path and the consequence.

Acceptance scenarios:
1. A yarn project with no readable root manifest yields no development seeds and one diagnostic saying classification was skipped.
2. A project with a readable manifest declaring no `devDependencies` is silent; an empty result is not a degradation.

### Edge Cases

bun: workspace monorepos keyed by path, `lockfileVersion` 2 with `configVersion`, the `overrides` map, a workspace member that is itself a dependency target, and JSONC trailing commas. yarn: v1 versus Berry dialects, Berry `workspace:` / `patch:` / `portal:` / `link:` / `file:` protocols under a development declaration, npm aliases, absent or unparseable root manifest, a manifest with no dev section, workspace members in both dialects, `workspaces` declared as an array or as an object with a `packages` list, a pattern matching a directory with no manifest, a member manifest that is unreadable while its siblings are fine, a member under an operator-excluded path, a member directory reached through a symlink, and a member whose development declaration is also a runtime declaration of the root or of another member.

## Requirements

### Functional Requirements

- **FR-001**: Resolve development declarations to locked package identity, not name alone, using each reader's existing identity rules.
- **FR-002**: Runtime reachability takes precedence over a development declaration, across all workspaces. A declaration reachable from any runtime or optional root is not development.
- **FR-003**: Optional and peer classification, and every existing non-development assignment, are unchanged. No package that is optional today becomes development.
- **FR-004**: bun development evidence is read from the lockfile's `workspaces` map, for every workspace path it contains, and requires no manifest on disk.
- **FR-005**: yarn development evidence is read from `package.json` files on disk for both dialects, because neither dialect records the axis. No development status is inferred from the lockfile. FR-009 governs which manifests are read.
- **FR-006**: An absent or unreadable **root** yarn manifest yields no development seeds, preserves current classification, and emits one operator-visible diagnostic naming the reader and the path, and reporting how many declarations were skipped under FR-012. A manifest that declares no development dependencies is not a degradation and is silent. Member manifests are governed by FR-010, not by this requirement.
- **FR-007**: The same project read through `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` and `bun.lock` classifies the same package set, to the extent each lockfile resolves the same versions. A disagreement this feature introduces is a defect and blocks it. A disagreement that predates it is measured, recorded in `measurements/`, and filed as its own issue; this spec names such a disagreement rather than implying a consistency the feature does not deliver.
- **FR-008**: Existing scope carriers in all three output formats express the classification. No new output field, no new annotation, and no new dependency.
- **FR-009**: yarn development evidence is collected from the root manifest and from every workspace member's manifest, in both dialects. Berry member locations are taken from the member entries the lockfile already records; v1 names no members, so their locations come from expanding the root manifest's `workspaces` patterns, which may be given as an array or as an object with a `packages` list. Both spellings are accepted by both dialects and must be handled.
- **FR-010**: An unreadable individual member manifest degrades that member only: its declarations contribute no development seeds, the rest of the workspace is classified normally, and one diagnostic names the member. A `workspaces` pattern matching a directory with no manifest is normal and silent.
- **FR-011**: Member discovery honours the operator's path exclusions and the traversal safety guarantees the scanner already provides, including symlink-loop protection and depth limits. A member under an excluded path contributes no development evidence and emits one diagnostic naming the exclusion, so a deliberately narrowed document is distinguishable from one that is silently unclassified. Member discovery introduces no traversal that bypasses these guarantees.
- **FR-012**: A development declaration seeds classification only when it resolves to a package the lockfile actually locks, identified in that lockfile's own package map. A declaration using a non-registry protocol — a sibling workspace, a local link, a portal, a filesystem path — contributes no seed and no identity is synthesised for it. This is normal operation, not degradation, and is silent. The accepted cost is recorded under Assumptions and Scope.

### Key Entities

**Workspace declaration set**: one workspace's direct `dependencies`, `devDependencies` and `optionalDependencies`, from the bun lockfile or a yarn manifest. **Package identity**: canonical name plus resolved version under each reader's existing normalization. **Runtime closure**: identities reachable from any runtime or optional declaration. **Development seed**: a direct development identity outside that closure. **Manifest evidence**: the yarn-only `package.json` input, which may be absent.

## Success Criteria

- **SC-001**: A yarn scan and a bun scan each assign development scope to at least one component where both assign none today. The zero baseline is recorded against `6bbd51e` in `measurements/findings.md`.
- **SC-002**: For every committed fixture, `--exclude-scope dev` removes the dev-only closure and retains the runtime closure, with before and after component counts recorded in `measurements/`. Counts are established by the task that authors each fixture rather than quoted here. Fixtures are hand-written from the measured shapes, because synthetic coordinates cannot be resolved by a package manager.
- **SC-003**: The v1 and Berry readings of one manifest produce identical classification. Both are compared against the `package-lock.json` **and** `pnpm-lock.yaml` readings of the same manifest — all four lockfiles FR-007 names — and every difference is either absent or enumerated in `measurements/` with its cause and issue number (FR-007). An unexplained difference fails this criterion.
- **SC-004**: In a monorepo whose development dependency is declared only by a workspace member, that dependency is classified as development by all three of yarn v1, yarn Berry and bun. The probe records that this dependency is resolved into every one of those lockfiles today and classified by none of them.
- **SC-005**: Every edge case above has an explicit regression control that fails if its behaviour changes, including a bun `lockfileVersion` 2 fixture, which no existing fixture provides.
- **SC-006**: A project whose yarn manifest cannot be read emits the FR-006 diagnostic, and a project with one unreadable workspace member emits the FR-010 diagnostic while still classifying its siblings. Both are demonstrated by tests that fail if the diagnostic is removed.
- **SC-007**: A member under an excluded path contributes no development seeds and emits the FR-011 diagnostic, and member discovery adds no traversal that escapes the exclusion or safety guarantees. Both are demonstrated by tests that fail if the behaviour changes.
- **SC-008**: A development declaration using each non-registry protocol produces no development seed and no synthesised identity, pinned by a test — so the FR-012 limitation is asserted behaviour rather than an accident of the implementation.
- **SC-009**: The mandatory pre-PR gate passes, or the exact blocker is reported without claiming readiness.

## Assumptions and Scope

Lockfile-wide scope is the union across a lockfile's workspaces, matching the pnpm v9 precedent and existing lockfile-wide emission. Workspace members are in scope for both yarn dialects (FR-009), chosen over a root-only reading because the two dialects would otherwise classify one project differently, which FR-007 calls a defect, and because bun gets members from its lockfile for free — a root-only yarn would disagree with bun on the same monorepo. The measured dialects are the supported ones: yarn 1.22.22, yarn 4.18.1 and bun 1.4.2; older bun `lockfileVersion` 1 files remain covered by existing fixtures rather than by this feature's probe. Fixtures use synthetic `waybill-fixture-*` coordinates; the probe in `measurements/` uses real ones because a synthetic name cannot be resolved by a package manager. pnpm and `package-lock.json` behaviour is unchanged — they appear here only as the FR-007 consistency reference. A known limitation is accepted under FR-012: a development dependency declared through Berry's `patch:` protocol wraps a real registry package, but because the declaration does not resolve to an entry in the lockfile's package map it contributes no development seed, so such a dependency stays unclassified. This is preferred over defining per-protocol target resolution that no reader performs today, and over asserting a descriptor shape that has not been measured. Whether `patch:` is worth handling is a separate question, to be answered by measuring the descriptor first. **Measured during implementation, and the limitation is stronger than this paragraph assumed**: a `patch:` descriptor carries a second `@` — `name@patch:name@npm%3A1.0.0#...` — which defeats the reader's descriptor-to-name split, so the package is not merely unclassified, it is never emitted as a component at all. FR-012 and SC-008 hold either way; recorded in `measurements/findings.md` and asserted by test, so the limitation cannot drift into an accident.

Issue #1297's own reader table omits the bun reader; correcting the issue is part of closing it.
