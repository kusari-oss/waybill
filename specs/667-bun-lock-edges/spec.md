# Feature Specification: bun.lock transitive-edge emission

**Feature Branch**: `667-bun-lock-edges`
**Created**: 2026-08-27
**Status**: Draft
**Input**: User description: "Fix bun.lock reader to emit transitive dependency edges (closes issue #723). Read the third tuple element of each `packages` entry and populate `PackageDbEntry.depends` from all four dep-section families (dependencies, peerDependencies, optionalDependencies, optionalPeers). Implement bun's non-hoisted key-path resolver so multi-version copies attach edges to the correct copy. Handle scoped-name two-segment paths. Tag optional/optional-peers with `LifecycleScope::Optional` matching m180/m181 precedent. Update `docs/ecosystems.md` npm-row caveat."
**Closes**: #723

## Clarifications

### Session 2026-08-27

- Q: How should `PackageDbEntry.depends` be populated? → A: Option A — two-pass reader approach. Pass 1 builds a `HashMap<KeyPath, String>` of `<key-path> → "<name> <version>"` disambiguation strings for every emitted component. Pass 2 walks each parent's metadata dependencies, resolves each dep-name via the key-path walker, and appends the resolved `"<name> <version>"` string to the parent's `depends` field. The graph builder resolves these to target PURLs at edge-emission time via the existing secondary `name_to_purl` key at `scan_fs/mod.rs:635-644` (m087 for cargo, m147 issue #262 for npm). This matches the `package_lock.rs:261` convention exactly. *(Plan-phase R1 correction 2026-08-27: my initial Q1 answer said "PURLs directly," which was a misreading of `package_lock.rs:285` — the actual convention is `"<name> <version>"` strings, not PURLs. The implementation shape stays the same — single-mechanism, no new emit-time hook — only the disambiguation-string format is corrected.)*

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Bun-lockfile-only scan produces a complete dep-graph (Priority: P1) 🎯 MVP

An SBOM consumer scans a Bun project (single or multi-workspace) whose only edge source is `bun.lock` — no network, no populated `node_modules/`. Every registry package the lockfile records is reachable through the emitted graph, so the SBOM's `graph completeness = complete`, no components carry `waybill:orphan-reason=hoisted-unused` on the sole basis that a parent lockfile-declared edge was dropped, and `dependencies[]` reflects the real transitive tree (each parent points at every child the lockfile declares, at the correct version copy).

**Why this priority**: This is the whole point of the fix. Direct edges already work; the reader ships a component set that matches `bun pm ls --all` exactly. What's missing is the parent-to-child edges declared inside each `packages` entry's own metadata. Restoring them (a) inverts the triage signal from wrong-by-default to right-by-default for every downstream consumer, (b) unblocks the `docs/ecosystems.md` promise of "Lockfile (full tree)" for the npm ecosystem row, and (c) matches the behavior every sibling npm-family reader already delivers.

**Independent Test**: run `waybill sbom scan --path <bun-monorepo> --offline --format cyclonedx-json --output out.cdx.json` on the reporter's minimal 2-file repro from issue #723 (a `package.json` declaring `parent-pkg`, a `bun.lock` declaring `parent-pkg` with a nested `dependencies: {"child-pkg": "^1.0.0"}`, and a `child-pkg` entry). Post-fix output shows: (a) `graph completeness computed value=complete reachable_count=3 total_count=3 orphan_count=0`, (b) `dependencies[]` includes an edge `pkg:npm/parent-pkg@1.0.0 -> pkg:npm/child-pkg@1.0.0`, (c) `child-pkg` carries no `waybill:orphan-reason` annotation. The pre-fix output (baseline from #723) shows the inverse — `partial`, `orphan_count=1`, `hoisted-unused` on `child-pkg`, no edge — so the delta between pre-fix and post-fix output for the identical fixture IS the fix.

**Acceptance Scenarios**:

1. **Given** the minimal 2-file repro from #723 (single non-workspace `package.json` + a `bun.lock` with parent→child transitive edge), **When** the operator scans with `--offline --format cyclonedx-json`, **Then** the emitted CDX contains a `dependencies[]` entry with `ref: pkg:npm/parent-pkg@1.0.0`, `dependsOn: [pkg:npm/child-pkg@1.0.0]`, and `child-pkg@1.0.0` is not annotated with any `waybill:orphan-reason`.

2. **Given** a Bun monorepo whose lockfile encodes the same package name at multiple versions under different non-hoisted parent key paths (e.g., `"minimatch"` at the root AND `"foo/bar/minimatch"` at a different version deeper in the tree), **When** the operator scans, **Then** the parent-at-`foo/bar` points at the DEEPER `minimatch` copy (matching bun's install-chain resolution order — most-specific prefix wins), and the parent-at-root points at the ROOT `minimatch` copy; neither edge misroutes to the other version.

3. **Given** a `bun.lock` whose parent entry declares `optionalDependencies: {"unicorn-terminal": "^1.0.0"}` (which the m180/m181 precedent expects to carry `LifecycleScope::Optional`), **When** the operator scans, **Then** the emitted CDX has the parent→unicorn-terminal edge with the same `waybill:optional-derivation = "npm-optional-dependencies"` annotation and target-side `waybill:lifecycle-scope = "optional"` that `package_lock.rs` produces for the equivalent `package-lock.json` shape (byte-identity of the classifier output across lockfile formats — the fix parity-bridges bun into the m180 pattern).

4. **Given** a scoped-name transitive edge (parent declares `dependencies: {"@types/node": "^22"}` and the lockfile keys the child copy at a two-segment scoped path like `"@fast-csv/format/@types/node"`), **When** the operator scans, **Then** the resolver correctly walks the parent's key prefix WITH the two-segment scope shape preserved (a naive single-`/`-split resolver would miss this) and emits the edge to the correct scoped-name PURL at the correct version copy.

5. **Given** any `bun.lock` fixture that pre-fix produced `graph completeness = partial` solely because of the missing lockfile edges (no other completeness signals contributing — no `--warm-go-cache` failures, no `--sbom-source referrer` fallbacks), **When** the same fixture is re-scanned post-fix, **Then** `graph completeness = complete` and the `waybill:graph-completeness-reason` annotation is absent (the m158/m167 orphan-reason classification pass finds zero orphans for the affected components).

### Edge Cases

- What happens when a `packages` entry's metadata object is present but has an empty `dependencies` map? (The parent SHOULD emit zero outgoing edges; the reader must not synthesize phantom edges to lookalike lockfile keys.)
- What happens when a metadata object references a dep-name that DOES NOT appear anywhere in the top-level `packages` map (e.g., the lockfile is inconsistent because a manual edit dropped a package)? (The reader must warn-and-continue per FR-010 of the m106 spec — emit a `tracing::warn!` naming the missing target, drop the edge, do NOT synthesize a component.)
- What happens when the metadata object's third-position slot is malformed (not an object, missing, integer)? (Warn-and-skip the edge extraction for THAT entry; still emit the component from the first-position spec.)
- What happens when `packages` contains a peerDependency to a name that matches an `overrides` entry? (The override wins per m106's existing override-resolution semantics; the edge target must reflect the OVERRIDDEN version, not the metadata-declared range.)
- What happens when a workspace member's `package.json` version conflicts with a `packages` entry that pins the same name to a different version? (The pre-fix reader already skips duplicate workspace entries at `bun_lock.rs:228` — the fix must preserve that behavior; the edge-emission pass must NOT create an edge to the workspace-shape component's PURL when the parent's dep-name resolves to a workspace member.)
- What happens when a parent key path contains an unusual segment (e.g., `"foo/bar/../baz"` — bun does not produce such paths, but the resolver must not crash on hand-edited lockfiles)? (The resolver must treat the key path as opaque string segments — no path canonicalization — because bun's key semantics are lexical, not filesystem-relative.)
- What happens when a parent entry has a nested `dependencies` map where a value is `null` or `""` (empty range)? (Warn-and-skip that specific edge; do NOT drop the entire parent's edge set.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The bun.lock reader MUST read the third tuple element (`packages[K][2]`) — the metadata object — of every `packages`-map value and extract its `dependencies`, `peerDependencies`, `optionalDependencies`, and `optionalPeers` sub-maps as edge sources. Pre-fix this position is entirely unread; post-fix it is the sole source of transitive edges (workspace edges continue to come from step 1's `workspaces` map).
- **FR-002**: For each parent-package at lockfile key `K` and each dep-name `X` extracted from `K`'s metadata object, the reader MUST resolve `X` to a specific `packages`-map key by walking `K`'s slash-separated key path from most-specific to root, returning the first `<K-prefix>/<X>` key that exists in the top-level `packages` map (matching bun's node_modules install-chain resolution order). If no prefix walk hits, fall back to the bare `X` key (root-hoisted lookup). If NEITHER resolves, warn-and-drop that single edge per FR-011.
- **FR-003**: The resolver MUST correctly handle scoped-name two-segment paths in both the parent key AND the dep-name. Given parent key `"@fast-csv/format/@types/node"`, resolving dep-name `"tslib"` MUST try (in order): `"@fast-csv/format/@types/node/tslib"`, `"@fast-csv/format/@types/tslib"`, `"@fast-csv/format/tslib"`, `"tslib"`. The resolver MUST NOT split on `/` naively — the `@scope/name` shape occupies two segments and each MUST be treated as a unit during the prefix walk.
- **FR-004**: Once the target key is resolved (per FR-002/FR-003), the reader MUST populate `PackageDbEntry.depends: Vec<String>` on the PARENT entry with a `"<name> <version>"` disambiguation string (SPACE-separated; matching the `package_lock.rs:261` convention verbatim). Implementation shape (per Clarifications 2026-08-27 Q1 + R1 correction): **two-pass reader**. Pass 1 walks the `packages` map once to build a `HashMap<KeyPath, String>` where each value is the emitted component's `format!("{name} {version}")` string. Pass 2 walks the `packages` map again, and for each parent with a metadata object, resolves each dep-name via the FR-002/FR-003 key-path walker → target `KeyPath` → target disambiguation string (via the pass-1 map), and appends that string to the parent's `depends` vector. The graph builder at `scan_fs/mod.rs:897` resolves these strings to target PURLs at edge-emission time via the pre-existing secondary `name_to_purl` key `(ecosystem, "<name> <version>")` (built at `scan_fs/mod.rs:635-644` for cargo/npm/golang since m087/m147). No new emit-time resolver hook is introduced.
- **FR-005**: Multi-version integrity: given a lockfile that legitimately encodes the same package name at N distinct versions under N different parent key paths (a real state Bun uses when different subtrees pin incompatible versions), the fix MUST produce N distinct edges, each landing on the correct version copy per FR-002's resolution order. A regression where all N edges collapse to the same version copy MUST be caught by unit tests before landing.
- **FR-006**: Edges extracted from `optionalDependencies` and `optionalPeers` sub-maps MUST tag the TARGET component's `lifecycle_scope` with `LifecycleScope::Optional` AND emit the `waybill:optional-derivation` annotation with the reader-specific string that identifies bun as the derivation source (matching the m180 pattern where `package_lock.rs` emits `"npm-optional-dependencies"` and yarn emits `"yarn-optional-dependencies"` — bun's string SHOULD be `"bun-optional-dependencies"` and `"bun-optional-peers"` respectively). The EDGE itself MUST be represented as `RelationshipType::OptionalDependsOn` (m179) so downstream emitters (CDX `scope: "optional"`, SPDX `OPTIONAL_DEPENDENCY_OF`, SPDX 3 `LifecycleScope::Optional` on the relationship) all light up per the shared m180 pipeline. Edges extracted from `peerDependencies` (not `optionalPeers`) MUST NOT be tagged optional — they are hard peer requirements per npm semantics.
- **FR-007**: The fix MUST preserve every pre-fix behavior on the workspace path (workspace-member emission at `bun_lock.rs:105-197`, intra-workspace `workspace:*` edges at lines 131-148, workspace-root synthesis, override resolution semantics). No regression on the m106 US2 acceptance test set. Post-fix the reader emits a SUPERSET of pre-fix edges: strictly more edges from the `packages`-map walk, zero fewer edges from the `workspaces`-map walk.
- **FR-008**: The fix MUST NOT introduce new components. Every edge target MUST resolve to a `packages`-map key whose component the pre-fix reader already emits. If a parent's dep-name resolves to a target that has no component (lockfile inconsistency), the reader MUST warn-and-drop that single edge per FR-011 — NOT synthesize a phantom component.
- **FR-009**: The fix MUST NOT touch the reader's inventory pass (the `packages`-map component-emission loop at `bun_lock.rs:205-279`). Post-fix `components.len()` for any given fixture equals pre-fix `components.len()`. All new work is edge-emission-only.
- **FR-010**: The fix MUST warn-and-continue on every malformed input case named in "Edge Cases" (missing metadata object, malformed metadata object, dep-name pointing at nowhere, null/empty range, unusual key-path segment). No panic, no early-return-from-parser, no dropped components. The pre-existing FR-010 warn-and-continue posture from m106 US2 applies uniformly.
- **FR-011**: Every dropped edge MUST emit a `tracing::warn!` line naming the parent key, the dep-name, and the reason (unresolved / malformed / null-range / etc.). This supports operator triage — a scan that "lost" edges should say so explicitly per Constitution X (Transparency).
- **FR-012**: `docs/ecosystems.md`'s npm ecosystem row MUST be updated in the same PR to reflect the corrected behavior. If the row already asserts "Dep-graph: Lockfile (full tree)" for the npm family broadly, the update MAY be a no-op OR a clarifying footnote confirming all three lockfile formats (`package-lock.json`, `pnpm-lock.yaml`, `bun.lock`) now honor the promise. If the row carries a bun-specific caveat (unlikely given the reporter's observation), the caveat MUST be removed.

### Key Entities

- **Bun `packages` entry (existing)**: 4-tuple JSON array. Position 0: `<name>@<source-spec>` string (used by pre-fix reader for name + version). Position 1: registry URL or empty. Position 2: metadata object with `dependencies` / `peerDependencies` / `optionalDependencies` / `optionalPeers` — **the fix's edge source, unread pre-fix**. Position 3: integrity hash (used for hash emission if we ship that in a follow-up; not scoped to this feature).
- **Bun key path (existing lockfile semantic, newly exercised by the fix)**: slash-separated string identifying a `packages`-map entry. Hoisted packages have single-segment keys (`"lodash"`); non-hoisted copies have multi-segment install-chain keys (`"madge/dependency-tree/precinct"`). Scoped names occupy two segments per scope (`"@fast-csv/format"` is one two-segment scope; `"@fast-csv/format/@types/node"` is a scope-prefixed nested scope).
- **Bun key-path resolver (new to this fix)**: pure function `resolve(parent_key: &str, dep_name: &str, packages_keys: &HashSet<&str>) -> Option<&str>` that walks `parent_key`'s scope-aware prefix from most-specific to root, returning the first key in `packages_keys` that matches `<prefix>/<dep_name>` (or bare `dep_name` at root). Deterministic; no filesystem access; no caching required.
- **`PackageDbEntry.depends: Vec<String>` (existing)**: the fix populates this on non-workspace-member entries with resolved edge targets (per FR-004 — either target PURLs directly, or stable identifiers the graph builder resolves at emit time). Pre-fix this field is `Vec::new()` at `bun_lock.rs:256`.
- **`LifecycleScope::Optional` + `RelationshipType::OptionalDependsOn` (existing, m179)**: the target-side tag and edge-type the fix reuses for optional/optional-peers per FR-006. No new variants introduced.

## Assumptions

- **The reporter's investigation is correct.** Their source-code trace (`bun_lock.rs:256` hardcodes `depends: Vec::new()`; the metadata object at tuple position 2 is unread) matches what I verified directly during the bug triage. The fix scope IS "read the metadata object and populate depends" — no hidden second bug is masking the observed behavior. If a hidden second bug exists (e.g., a downstream graph-builder that silently drops non-workspace edges even when the reader emits them), it will surface during SC-001 verification and the plan phase will need to address it.
- **Bun's key-path resolution matches node_modules install-chain semantics.** The reporter states this and it matches Bun's documented behavior (`bun install --backend=hardlink` and the `--linker=isolated` mode both key non-hoisted packages by their install chain). If a future Bun version changes the semantics, the resolver may need to adapt, but the semantics as of Bun 1.2 (the version m106 targeted) are frozen for this fix.
- **The four dep-section families exhaust the edge sources.** `dependencies` + `peerDependencies` + `optionalDependencies` + `optionalPeers` are what `package_lock.rs` walks (m180) and what the reporter's investigation names. If future Bun versions add a fifth section (unlikely — npm's own vocabulary has been frozen for years), the reader will silently drop those edges until a follow-up spec extends the family list.
- **The scoped-name resolver's two-segment shape is stable.** `@scope/name` is the npm spec's canonical scoped-name shape and applies uniformly across all npm-family lockfiles. No exotic scope shapes (`@scope@version/name`, etc.) exist in the wild that this fix would need to handle.
- **Optional / optional-peer semantics match the m180 pattern.** The npm ecosystem's optional-dep vocabulary (`LifecycleScope::Optional` + `RelationshipType::OptionalDependsOn` + `waybill:optional-derivation` annotation) is what the fix reuses. If bun's optional semantics diverge from npm's (e.g., Bun treats optionalPeers differently than npm does), the fix will match npm's semantics as codified in m180 and any bun-specific divergence will be filed as a follow-up.
- **The fix will land as a standalone PR against `main`**, not bundled with unrelated work. The scope (one reader file + one docs file + tests + ecosystems.md caveat) is small enough that bundling would obscure the diff.
- **Pre-fix component-emission behavior is correct.** The reporter states the component set exactly matches `bun pm ls --all` and an independent lockfile parse. The fix will not touch the component emission loop (FR-009) — only the edge-emission behavior. If some component-emission bug is later discovered, that's a separate fix.
