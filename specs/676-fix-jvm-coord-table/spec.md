# Feature Specification: Accept coord-table `directDependencies` in Pants coursier-JVM lockfiles

**Feature Branch**: `676-fix-jvm-coord-table`
**Created**: 2026-09-03
**Status**: Draft
**Input**: User description: "Fix m224 Pants coursier-JVM reader — accept coord-table form of directDependencies (issue #756)"

**Scope expansion discovered at implement-time**: The bug is present in **both** `directDependencies` and `dependencies` fields. The issue #756 report only named `directDependencies`; the sibling `dependencies` field (which feeds the dep-graph edges) also uses the coord-table shape in real-world Pants coursier lockfiles. Feature 676 accordingly fixes both fields. See `research.md` R1 amendment for the details.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - SBOM operator scanning a real Pants JVM monorepo (Priority: P1)

An operator runs `waybill sbom scan` on a Pants monorepo whose `3rdparty/jvm/default.lock` was produced by any recent version of `pants generate-lockfiles`. Today, the scan silently drops the entire JVM resolve (zero `pkg:maven/*` components emitted) because the reader chokes on the coord-table form of `directDependencies` and skips the whole lockfile. The operator expects the SBOM to include every locked Maven coordinate declared in the resolve.

**Why this priority**: This is a total loss of coverage for the primary real-world Pants JVM use case. The bug affects **every** Pants JVM monorepo generated by current tooling — the coord-table shape is what `pants generate-lockfiles` emits by default. Pantsbuild's own official example repo (`pantsbuild/example-jvm`) hits this bug. P1 because the failure mode is complete silence (WARN log + zero components) with no operator-visible signal short of comparing SBOM output against the source lockfile by hand.

**Independent Test**: Scan the pantsbuild/example-jvm fixture at its pinned SHA. Verify the emitted SBOM contains `pkg:maven/*` components matching the resolve's `generated_with_requirements` header block. Zero `WARN pants-coursier-jvm reader: coursier TOML body parse error` log lines emitted.

**Acceptance Scenarios**:

1. **Given** a Pants monorepo with a `directDependencies = [{group, artifact, version}, ...]` coord-table shape in its coursier lockfile, **When** the operator runs `waybill sbom scan`, **Then** the emitted SBOM contains a `pkg:maven/<group>/<artifact>@<version>` component per locked coordinate.
2. **Given** the same monorepo, **When** the operator inspects the scan's stderr log at INFO level, **Then** the `pants-coursier-jvm reader complete` line reports `lockfiles_parsed_ok=N, lockfiles_skipped_corrupt=0, components_emitted=M` where M matches the resolve's declared coordinate count.

---

### User Story 2 - Reader robust across both empty-array and coord-table shapes (Priority: P2)

A Pants monorepo maintainer upgrades or downgrades their Pants version and regenerates their coursier lockfile. Different Pants versions emit `directDependencies` in different shapes (empty-array vs coord-table, sometimes mixed within the same lockfile when entries have varying dep-graph positions). The reader must not care — every legal coursier-lockfile shape must parse.

**Why this priority**: Regression prevention. Even after the fix lands, real-world Pants versions vary, and mixed-shape lockfiles are proven to exist (the `pantsbuild/example-jvm` fixture at `675ee75d` has both shapes in the same file, per the issue #756 reproduction). P2 because it's a hardening story, not a coverage story — US1 alone delivers the primary value.

**Independent Test**: A synthetic lockfile with three entries — one using empty-array, one using coord-table with a single coord, one using coord-table with multiple coords — parses successfully and emits three `pkg:maven/*` components.

**Acceptance Scenarios**:

1. **Given** a coursier lockfile with mixed `directDependencies` shapes (empty-array in some entries, coord-table in others), **When** the reader parses it, **Then** every entry becomes a `pkg:maven/*` component; no entry is silently dropped.
2. **Given** the same lockfile, **When** the reader completes, **Then** its structured completion log reports `lockfiles_parsed_ok=1` (not `lockfiles_skipped_corrupt=1`).

### User Story 3 - Re-enable pants-example-jvm corpus regression gate (Priority: P3)

The m195 public corpus harness gains a `pants-example-jvm` target (deferred in PR #757 pending this fix). Nightly CI thereafter catches any future regression in the coursier-JVM reader against a real-world upstream lockfile shape.

**Why this priority**: Follow-on regression protection. Not required for the fix itself to deliver its P1 value, but the corpus target's presence is the tracked follow-up that closes the loop between "we found this bug" and "we prevent it from silently returning".

**Independent Test**: The `pants-example-jvm` corpus target is added to `waybill-cli/tests/corpus_harness_195/manifest.rs`; its layer 1 assertions pass; goldens are generated + committed.

**Acceptance Scenarios**:

1. **Given** the fix from US1/US2 lands, **When** the maintainer adds a `pants-example-jvm` CorpusTarget entry pointing at the existing `kusari-sandbox/example-jvm` fork at SHA `675ee75d36f2c1b096b0def51efcfffd02bd1251`, **Then** `WAYBILL_RUN_PUBLIC_CORPUS=1 cargo test --test public_corpus corpus_pants_example_jvm` passes.
2. **Given** the corpus target exists, **When** a future contributor breaks the coord-table parse path again, **Then** the nightly CI corpus lane fails with a diagnostic pointing at the coursier-JVM reader.

### Edge Cases

- **Malformed coord-table entry** (missing `group`, empty `version`, non-string values): the reader should skip that individual entry with a WARN log naming the offending entry and lockfile, then continue emitting the other valid entries. Whole-lockfile skip is the pre-existing WARN behavior for TOML body parse errors; individual-entry validation errors should follow the same fail-open pattern but at finer granularity per the Constitution's principle III (fail-open at supplemental readers).
- **`directDependencies` field absent entirely**: existing behavior — treat as empty (no direct deps declared).
- **Legacy string-array form** (`directDependencies = ["group:artifact:version", ...]`) — if this shape is documented in any Pants version, preserve support alongside the coord-table shape. If it never appears in the wild, no-op.
- **`directDependencies` contains a mix of string-form and coord-table-form entries within the same array**: both must parse (the fix's untagged-enum approach handles this natively).
- **Lockfile with valid coord-table `directDependencies` in every entry but the `dependencies` field is missing or malformed**: the existing `dependencies` handling is unchanged by this fix; whatever it does today keeps doing.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The Pants coursier-JVM reader MUST accept `directDependencies` values in the coord-table array form (`[{group, artifact, version}, ...]`) without raising a TOML body parse error or skipping the enclosing lockfile.
- **FR-002**: The reader MUST continue to accept `directDependencies` values in the empty-array form (`directDependencies = []`) exactly as it does today.
- **FR-003**: The reader MUST parse lockfiles that mix the two shapes across different `[[entries]]` blocks — no lockfile that a running version of Pants can produce may be silently dropped.
- **FR-004**: When an individual coord-table entry is malformed (missing required field `group`, `artifact`, or `version`; type mismatch on a required field), the reader MUST log a WARN naming the lockfile path and skip that individual entry, continuing to emit the remaining valid entries. This matches the Constitution's fail-open convention for supplemental readers.
- **FR-005**: The structured `pants-coursier-jvm reader complete` INFO log (per existing m224 FR-011) MUST accurately report `lockfiles_parsed_ok`, `lockfiles_skipped_corrupt`, and `components_emitted` counts, including any per-entry skips.
- **FR-006**: The fix MUST NOT alter emitted PURL shape, dependency-edge shape, or annotation shape for lockfiles that already parse today under the empty-array form — output must be byte-identical for pre-fix passing fixtures.
- **FR-007**: New unit tests MUST cover: (a) coord-table with one direct dep, (b) coord-table with multiple direct deps, (c) mixed empty-array + coord-table within the same lockfile, (d) malformed coord-table entry warn-and-skip, (e) legacy string-form if preserved.
- **FR-008**: The `pants-example-jvm` corpus target MUST be re-added to the m195 harness at `waybill-cli/tests/corpus_harness_195/manifest.rs`, using the existing `kusari-sandbox/example-jvm` fork at SHA `675ee75d36f2c1b096b0def51efcfffd02bd1251`. Layer 1 assertions per contracts pattern established by PR #757.

### Key Entities

- **Coursier lockfile entry**: a single `[[entries]]` TOML block naming one locked Maven distribution. Fields: `coord` (group/artifact/version/packaging/classifier), `file_name`, `file_digest`, `directDependencies` (array — either empty or coord-table), `dependencies` (array). The `directDependencies` field's shape is the focus of this fix.
- **Coord reference**: within a coord-table `directDependencies` array, one `{group, artifact, version}` entry naming a specific Maven coordinate. Different from the `Entry.coord` shape (which also includes `packaging` and `classifier`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Scanning `pantsbuild/example-jvm` at SHA `675ee75d36f2c1b096b0def51efcfffd02bd1251` (via the `kusari-sandbox/example-jvm` fork) emits ≥ 20 `pkg:maven/*` components. Baseline observed in the issue #756 reproduction: 27 top-level `[[entries]]` blocks in the lockfile; the ≥ 20 floor allows ≤ 7-entry benign drift (lockfile refresh) before firing while catching any ≥ 25% regression.
- **SC-002**: Zero `WARN pants-coursier-jvm reader: coursier TOML body parse error` log lines fire on the pantsbuild/example-jvm fixture scan after fix.
- **SC-003**: Zero regression on any existing pants_jvm test fixture — all currently-passing tests continue to pass without modification.
- **SC-004**: New unit tests covering the coord-table shape land alongside the fix, with at least the 5 cases enumerated in FR-007.
- **SC-005**: The re-enabled `pants-example-jvm` corpus target's layer 1 assertions pass under `WAYBILL_RUN_PUBLIC_CORPUS=1`.
- **SC-006**: No new Cargo dependencies are added at the workspace level.
- **SC-007**: Fix code diff stays under 100 lines of production code in `waybill-cli/src/scan_fs/package_db/pants_jvm/` (bug fix scope discipline; the fix is small and targeted).

## Assumptions

- The Suggested-Fix "option A" from issue #756 — a `serde` untagged enum accepting both shapes — is the preferred approach because it is **strictly additive** and preserves any downstream use of the parsed `directDependencies` value (direct-vs-transitive classification, if wired to lifecycle-scope emission, or reserved for future use). The alternative — "option B" (drop parsing of `directDependencies` entirely and rely on `dependencies` for the graph) — is a valid simpler-but-riskier path; if fixture-in-code inspection reveals the field is unused downstream, planning may adopt option B instead. This decision surfaces at planning time via a research task, not spec time.
- The pantsbuild/example-jvm fixture at SHA `675ee75d36f2c1b096b0def51efcfffd02bd1251` is representative of "real Pants JVM monorepo output" — the fixture repo IS Pantsbuild's own JVM example. If a future Pants version generates a materially different lockfile shape, that's a separate follow-up.
- The `kusari-sandbox/example-jvm` fork exists at that SHA (created during PR #757 preparation; verified in that PR's task T004). No new fork is needed for this feature.
- The `Ecosystem::JavaMaven` variant of the m195 corpus manifest applies to Pants-JVM targets; no new ecosystem tag is introduced.
- Real-world Pants monorepos use the coord-table shape universally — no legacy-string-form fixture is available for empirical testing. If FR-007's clause (e) can't be exercised on any real fixture, a synthetic hand-authored lockfile is acceptable coverage.
- No changes required to `waybill-common/`; the fix is scoped to `waybill-cli/src/scan_fs/package_db/pants_jvm/`.
