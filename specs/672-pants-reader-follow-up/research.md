**Date**: 2026-09-01
**Status**: Complete — no unresolved NEEDS CLARIFICATION markers.

## R1 — Pants `//`-comment lockfile shape (pre-2.30)

**Decision**: Strip any run of leading lines whose first non-whitespace character is `//`. Stop at the first line whose first non-whitespace character is anything else (typically `{` opening the JSON object).

**Rationale**: Pants ≤ 2.29 prepended metadata as a comment block using `//` line-comments (per <https://www.pantsbuild.org/blog/2025/12/11/lockfile-metadata-files>). The block's *content* is Pants-specific tooling metadata (invalidation-hash of source PEP 508 reqs, etc.) that waybill has no reason to interpret. Stripping the prefix and handing the rest to `serde_json::from_slice` recovers the JSON body without waybill needing a Pants-metadata parser.

Concrete shape observed on the early adopter's `python-default.pants.lock`:

```text
// This lockfile was autogenerated by Pants. To regenerate, run:
//
//    ./pants generate-lockfiles --resolve=python-default
//
// --- BEGIN PANTS LOCKFILE METADATA: DO NOT EDIT OR REMOVE ---
// {
//   "version": 3,
//   "valid_for_interpreter_constraints": [...],
//   "generated_with_requirements": [...],
//   "manylinux": "manylinux2014",
//   ...
// }
// --- END PANTS LOCKFILE METADATA ---
{
  "allow_builds": true,
  "allow_prereleases": false,
  ...
}
```

Note two useful invariants:
1. Every metadata line begins with `//` (no exception — even the `// {` opening the embedded JSON in the metadata block is comment-marked).
2. The JSON body always starts at column 0 with `{`. There is no whitespace-only line between the metadata block and the JSON body in real-world Pants output, but the stripper tolerates any (per Edge Cases in spec).

**Alternatives considered**:
- **Retry-on-failure** (parse verbatim first; strip only on failure). Rejected in clarify Q3 — Option A (always-strip-first) chosen for uniform code path + easier WARN-log analysis.
- **Full Pants metadata parser** (read the metadata block into a `PantsMetadata` struct). Rejected — waybill doesn't consume the metadata; parsing it just adds surface area for future breaking changes.
- **Regex-based strip** (e.g. `^//.*$` multi-line). Rejected — depends on `regex` crate (already a workspace dep so not disqualifying) but slower + less explicit than a byte-level line scanner.

## R2 — Prefix-strip algorithm

**Decision**: Line-based `memchr`-style byte scan. Read bytes from position 0. For each line:
1. Skip leading whitespace bytes (space, tab).
2. Look at the next 2 bytes.
3. If they are `//`, advance to the next newline (`\n` — or CRLF `\r\n`), continue.
4. Otherwise, this line is the JSON body's start — return the slice from this line's first byte to end-of-input.

Implementation shape (~30 lines of `fn strip_pants_frontmatter(bytes: &[u8]) -> &[u8]`):

```rust
fn strip_pants_frontmatter(bytes: &[u8]) -> &[u8] {
    let mut pos = 0;
    loop {
        // Save the start of this line; we may need to return it as the body.
        let line_start = pos;
        // Skip leading whitespace within this line.
        while pos < bytes.len()
            && matches!(bytes[pos], b' ' | b'\t')
        {
            pos += 1;
        }
        // If we ran out of input, or this line doesn't start with `//`,
        // return the slice starting at this line's original position.
        if pos + 1 >= bytes.len() || &bytes[pos..pos + 2] != b"//" {
            return &bytes[line_start..];
        }
        // This line is a `//` comment. Advance to just past the next `\n`.
        match memchr::memchr(b'\n', &bytes[pos..]) {
            Some(offset) => pos = pos + offset + 1,
            None => return &[],
        }
    }
}
```

Complexity: O(prefix-length). On a clean-JSON file (first non-whitespace byte is `{`), the loop makes exactly one pass through step 4 and returns immediately — negligible overhead. On a `//`-prefixed file, the scan is bounded by the metadata-block size (typically < 4 KB for Pants), well under the 5-ms SC-007 budget.

**`memchr` availability**: The `memchr` crate is already in the workspace dependency closure (transitively via `serde_json`, `tokio`, and `regex`). No new direct dep. Alternative — hand-rolled `while pos < bytes.len() && bytes[pos] != b'\n' { pos += 1 }` — same asymptotic cost, ~2× slower on modern x86 due to no SIMD. Either shape satisfies SC-007; the implementer chooses.

**Alternatives considered**:
- **`str::lines()` after `std::str::from_utf8`**: rejected — forces a full-file UTF-8 validation up-front (O(file-length)); violates FR-003.
- **`std::io::BufRead::lines()` on a `Cursor`**: same UTF-8 issue + allocates a `String` per line.

## R3 — TOML `[python.resolves]` bare-string map parsing

**Decision**: Extend `PythonSection` in `pants/config.rs` with a new field:

```rust
#[derive(Deserialize)]
pub(crate) struct PythonSection {
    #[serde(default)]
    pub(crate) lockfile: Option<String>,        // existing (m223)
    #[serde(default)]
    pub(crate) resolves: BTreeMap<String, TomlValue>,  // NEW (m672)
}
```

Then, after `toml::from_str`, walk the `resolves` map, and for each entry:
- If the value is a `String`, add `(map_key, path_string)` to the discovery set.
- If the value is anything else, WARN once with the resolve name + observed TOML type + a migration hint, then skip that entry.

Using `toml::Value` for the map's value type (instead of `String` directly) accomplishes two things:
1. Serde deserialization SUCCEEDS on table-shape values (they land as `Value::Table`) — we don't fail the whole `pants.toml` parse.
2. We can name the observed type in the WARN message (`Value::Table`, `Value::Array`, `Value::Integer`, ...) — better operator UX.

**Rationale**: `toml = "0.8"` is already a workspace dep. `toml::Value` is its standard tagged-union type; deserializing into `BTreeMap<String, toml::Value>` gives us type-tolerant traversal. Using `BTreeMap` (not `HashMap`) preserves lexical key order for deterministic dedup + deterministic WARN log ordering (see Edge Cases in spec).

**Alternatives considered**:
- **Serde `#[serde(untagged)]` enum** with `String` and `Table` variants. Rejected — bigger blast radius (needs a bespoke enum + Deserialize impl), no operator UX benefit (we still WARN-and-skip on table shape).
- **Two-pass parse**: first pass into `BTreeMap<String, String>` (strict); on parse failure, second pass into `BTreeMap<String, toml::Value>` to name offending keys. Rejected — 2× the parse work for zero UX gain over the single-pass `toml::Value` approach.

## R4 — Path canonicalization + dedup semantics

**Decision**: When both the default glob AND `[python.resolves]` name paths that resolve to the same file, `std::fs::canonicalize` the two `PathBuf`s and dedup by the canonicalized form. When dedup fires, the `[python.resolves]`-declared `resolve_name` wins (matches FR-009 in spec).

Concrete flow inside `discover_lockfiles`:

1. Enumerate the default glob → `Vec<(PathBuf, /*resolve_name*/ String)>` where the name is `file_stem`-derived.
2. Enumerate `[python.resolves]` bare-string entries → `Vec<(PathBuf, /*resolve_name*/ String)>` where the name is the map key.
3. For each entry in (2), canonicalize its path. If the canonicalized form is already in the (1) set (also canonicalized), REPLACE the (1) entry with the (2)-form (map key wins). Else, append.
4. Also handle the legacy `[python].lockfile` singular field the same way (canonicalize + dedup against both sets).

`std::fs::canonicalize` follows symlinks (documented behavior). This matches the m054 `safe_walk` conventions and Pants's own path-resolution rules (Pants also follows symlinks under `pants.toml`-declared paths).

**Alternatives considered**:
- **`path-clean` crate** (purely lexical, no filesystem access). Rejected — doesn't handle symlinks, and both real-world adopters run in symlinked-repo setups (worktrees, monorepo tooling).
- **Two-set intersection with `HashSet<PathBuf>` on non-canonicalized paths**. Rejected — misses the symlink case + misses `./3rdparty/python/foo.lock` vs `3rdparty/python/foo.lock` (dot-prefix drift).

## R5 — FR-013 log-field emission on the reader-complete summary

**Decision**: Extend the existing `tracing::info!` at `pants/mod.rs:157–163` with one additional field:

```rust
tracing::info!(
    lockfiles_discovered,
    lockfiles_parsed_ok,
    lockfiles_skipped_corrupt,
    legacy_shape_lockfiles,   // NEW (m672 FR-013)
    components_emitted,
    "pants-pex reader complete"
);
```

Wire this by threading a `usize` counter through the parse loop — incremented every time the stripper actually consumed at least one `//` line (i.e., the returned slice is shorter than the input).

Also (per FR-010/FR-011/FR-012 + Q3), remove the early-return at `pants/mod.rs:111` for the zero-discovered case when at least one Pants signal is present. Specifically:

- If `default_dir.exists() || pants_toml.exists()`: fall through to the summary log even when candidates is empty, and include a hint field naming the two supported override keys.
- Else (neither signal present): keep the pre-m672 silent-return behavior (preserves m223 SC-003 byte-identity for non-Pants repos).

**Alternatives considered**:
- **New second log line for "zero-discovered"**: rejected — one log line per reader-invocation is easier to grep + consumes less log-line budget.
- **DEBUG-level per-file field showing which files were legacy shape**: nice-to-have; deferred to a v2 milestone. The v1 summary counter is sufficient for the "nudge operator to regenerate" use case.

## R6 — Fixture strategy

**Decision**: Synthetic `tempfile::tempdir()` fixtures inside the integration test file at `waybill-cli/tests/scan_pants_m672.rs`. Package names use the `waybill-fixture-*` prefix (per memory `feedback_fixture_synthetic_package_names`). No new committed fixtures under `waybill-cli/tests/fixtures/`.

Minimum fixture shapes (composed at test runtime):

1. **US1 legacy `//`-shape**: a `3rdparty/python/legacy.lock` file starting with a metadata `//` block matching R1's observed shape, followed by a valid `{"pex_version": "2.10.0", "locked_resolves": [...]}` body naming 2 synthetic packages. Asserts both are emitted + `resolve_name=legacy`.
2. **US1 fail-open**: same shape but the JSON body after the `//` block is malformed (extra `,`). Asserts WARN + skip + zero components + scan-exit 0.
3. **US2 `[python.resolves]` map**: a `pants.toml` with `[python.resolves] mypy = "build-support/py/mypy.lock" user_reqs = "3rdparty/python/user_reqs.lock"` + two valid lockfiles at those paths. Asserts both emit + resolve names match the map keys.
4. **US2 dedup**: same repo but `mypy` in `[python.resolves]` points at a file ALSO under the default glob. Asserts single-parse + `resolve_name=mypy` wins over file-stem-derived name.
5. **US2 non-string value**: `pants.toml` with `[python.resolves.internal-libs] path = "..."` (table shape). Asserts WARN naming both `internal-libs` and observed `table` type, no components emitted from that entry.
6. **US3 zero-discovered-with-signal**: a repo with `pants.toml` present but no lockfiles at any declared path. Asserts one INFO log line with `discovered=0` + the hint text naming the two override keys.
7. **US3 no-Pants-signal**: an empty directory. Asserts zero log lines from the pants reader.
8. **Byte-identity guard (SC-003)**: reuse the m223 `waybill-cli/tests/scan_pants_pex.rs` golden path — assert the same fixture emits the same components after m672 lands (no diff).

**Rationale**: Every fixture composable in-test avoids the m090 fixture-repo dance (`~/.cache/waybill/fixtures/<sha>/`) which is heavy for a 4-file reader extension. Synthetic package names avoid Kusari Inspector advisory noise per the memory-recorded fixture policy.

## R7 — Alignment with the m223 shape-1 acceptance contract

The m223 reader emits one `PackageDbEntry` per (pex_lockfile, locked_requirement) tuple via `lockfile::locked_req_to_entry`. m672 does NOT change that shape — components emitted from legacy-shape files OR from `[python.resolves]`-declared paths carry the same PURL shape (`pkg:pypi/<project_name>@<version>`), the same `resolve_name`-tagged annotations, and the same evidence attachment. Only the SOURCE (which files feed the discovery loop) changes; the OUTPUT (component shape per file) is preserved bit-for-bit.

This means the existing m223 parity extractors + emission tests apply unchanged. No new parity-catalog work + no C-row registration needed for v1 (matches Q1 clarification).
